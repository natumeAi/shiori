# S3 iPhone 设备验收步骤

用于 S3-AC10 及其他 AC 的真机部分。2026-10-27 用户确认实机测试全部通过，
S3 已据此收尾，详见 [验收结论与证据边界](s3-closeout.md)。
以下保留原始操作步骤与空白模板，不代表仍有待办，也不补造逐项测量数据。
每步记 `pass / fail / partial / unverified`；失败保留现场，可继续独立项目。
真实地址、书名、截图、录屏和诊断只放在忽略目录 `local-evidence/s3/`。
本文中 `<NAS_ROOT_URL>`、`<BUILD_REF>` 等均为占位符，操作时自行替换。

## 0. 开始前：用户与协调者各自准备

1. 用户：iPhone 连到可访问 NAS 的 Wi-Fi，准备一本普通 EPUB、一个有书的文件夹，
   确认现有 Shiori probe 可启动；保存原有诊断导出和留存标记的截图。
   准备原先全能签使用的证书与描述文件；密码、证书、团队信息不发到聊天或 CI。
2. 协调者：先完成主 checkout 的最终检查。待发布提交必须包含 S3 A–E 全部实现：
   当前基线为 `3c40f65`，包括产品 UI `4f1ee69`、`ae723b4`、
   app 构建模式 `5eb04c0` 和最后的租约修复 `3c40f65`；若后续有修复也须包含。
   构建前给用户展示最终 `<FULL_SHA>`、`<BUILD_REF>` 和待推送差异。
3. **公开 push 须有用户对具体分支及提交的明确授权。** Phase A 对
   `f94664c`、`c018794` 的既有授权不代替本轮授权。由协调者在获授权后发布；
   本文编写不执行 commit、push 或分支切换。
4. 用户在电脑本地准备 `local-evidence/s3/`；协调者确认该目录仍被 Git 忽略。
   只记录设备型号、iOS 版本、全能签版本；签名身份仅记“与原安装一致/不一致”。

## 1. 协调者：生成产品包

1. 将获授权的完整提交发布到 `<BUILD_REF>`。`ios-build/**` 的 push 自动构建的是
   **probe**，不能用它替代本次产品验收。
2. 在 Actions 的 **Unsigned iPhone probe → Run workflow** 中选择该 ref，
   输入 `mode=app`。协调者也可执行：

   ```powershell
   gh workflow run ios-unsigned.yml --ref <BUILD_REF> -f mode=app
   ```

3. 确认运行对应 `<FULL_SHA>`，摘要为 `app`、`lib/main.dart`；使用现有免费 hosted
   路线，不上传 Apple 签名材料。若 dispatch 不可用，记录阻塞交协调者处理。
4. 成功后下载 artifact `shiori-app-<full sha>-gha-<run number>`（保留 14 天）。
   内含一个 `shiori-app-<12-character sha>-gha-<run number>.ipa`。

**预期 / 记录：** 构建成功；保存 run、commit、build ID、build number、构建记录。

## 2. 下载后先核对，再传到手机

1. 解压 artifact。核对 `provenance.json` 的 commit、build ID、build number、
   `mode=app`、`entryPoint=lib/main.dart`；`build-exit-code.txt` 必须为 `0`。
2. `bundle-info.txt` 应为 `iphoneos`、`io.github.natumeai.shiori`，
   `CFBundleVersion` 对应 run number；检查本地网络用途说明存在。
   构建日志须通过 arm64、Framework/SQLite 和 IPA ZIP 校验，产品使用默认 Metal 层。
3. 在电脑核对 IPA SHA-256 与 `sha256.txt`、provenance 中该文件的值一致：

   ```powershell
   Get-FileHash -Algorithm SHA256 '<IPA_PATH>'
   ```

4. 审阅 `ios-status.txt`、`ios-project.diff`，以及存在时的 `ios-untracked.zip`。
   异常或未审阅的原生迁移交协调者处理；失败运行可能也有 artifact，不安装残包。
   将核对通过的 IPA 经自己的文件传输方式保存到 iPhone“文件”。

**预期 / 记录：** 来源、身份、校验均匹配；保存校验结论与包大小。
Phase A SQLite 探针已通过六步自检；本轮须另记产品包实际启动和持久化结果。

## 3. 用户：用全能签覆盖现有 probe

1. 从“文件”分享/导入 IPA 到全能签。使用原证书、原描述文件，保持
   `io.github.natumeai.shiori`、版本和构建号；关闭注入及补丁，核对实际签名身份。
   如工具自动改写配置，记下改动交协调者判断。
2. **直接覆盖安装，不卸载旧应用。** 若证书团队或实际 bundle ID 不一致，
   或提示必须删除旧应用，停止更新留存项，记录原因；不要清数据来通过验收。
   按现有签名类型完成必要的信任/开发者模式操作。
3. 从桌面启动，应出现“连接书库”等产品界面，而非 probe 菜单。
   在“文件”检查原有 Documents 诊断导出仍在、内容未变。

**预期 / 记录：** 覆盖、独立启动成功，旧导出保留；记录实际安装 build number
与签名身份一致性。产品界面不能查看旧 probe 标记时，将该标记留存单独记为
`unverified`，不降级安装 probe 检查，也不把文件可见当作全部状态保留。

## 4. 首次连接：拒绝本地网络，再恢复（AC2/AC10）

1. 在连接页输入 `<NAS_ROOT_URL>`，点“连接”。系统询问本地网络权限时先拒绝。
   弹窗可能直到第一次 LAN 请求才出现；记录实际出现时机。
2. 应显示可恢复的连接失败，页面仍能操作；不能把一般网络错误认定为权限诊断。
3. 到 iPhone“设置 → 隐私与安全性 → 本地网络”，开启 Shiori；返回应用再次点
   “连接”。应能继续成功，无需重装或改包。

**记录：** 拒绝、开启、重试各自结果和耗时，以及弹窗/错误截图编号。
若旧安装已有权限而未弹窗，不卸载或重置全部隐私设置；关闭开关测试失败再开启，
把“首次弹窗/点击拒绝”单独记 `unverified`，不要用开关测试冒充首次弹窗证据。

## 5. NAS 地址与书库（AC1/AC4/AC9/AC10）

1. 使用部署根 `<NAS_ROOT_URL>`，包含实际协议、端口和已有路径前缀；
   不填管理页、书籍页或 `/api/...`，不夹带用户名、密码、查询串。
2. 连接后检查书库列表、普通书籍信息、至少一个封面。已有无封面书籍时检查占位图，
   不为此修改服务端。进入一个文件夹，再返回；应显示对应内容且导航正常。
3. 点“刷新书库”，完成后仍能浏览。检查键盘收起、返回、较大文字及系统明暗模式下
   按钮可见可用；只记录观察结果。

**预期 / 记录：** 真机经实际传输取得列表、封面和文件夹内容；记录成功/失败数，
用“服务器 A / 普通书 A / 文件夹 A”代号，不抄真实 URL、书名或作者。
根部署、带前缀部署、纯 HTTP 分别记结果；仅测试用户已有部署，
无对应部署的项目写 `unverified（未提供）`，不新建代理、不改 NAS/TLS/ATS 配置。

## 6. 断网与恢复（AC2/AC4/AC9）

1. 先成功加载列表，再从“设置”关闭 Wi-Fi，确保蜂窝/VPN 等也没有可达 NAS 的路径。
   返回应用点“刷新书库”。
2. 应保留已保存的列表，显示“内容可能不是最新的”等 stale 提示及可恢复错误，
   不清空原服务器、不无限卡住。
3. 恢复 Wi-Fi，点“重试”或“刷新书库”；成功后 stale 提示应消失。

**记录：** 断网错误、旧列表是否保留、恢复耗时、提示是否清除。
此项只证明已加载元数据的暂存浏览，不代表离线冷启动或完整离线阅读。

## 7. 普通书：取消、重试、准备完成（AC5/AC7/AC9/AC10）

1. 打开“普通书 A”，点“准备此书”。在准备中点“取消”；应回到可操作状态，
   不把取消显示为成功，也不在稍后突然冒出旧任务的成功/错误。
   若书太小来不及取消，记录未覆盖，可用下一节大样本重试。
2. 再点“准备此书”（失败状态点“重试”），等待下载和内容检查全部完成。
   应显示“书籍已下载并检查完成。阅读器可用后即可打开。”
3. 点“重新准备”再完成一次；返回列表，再进入该书，应能恢复可用状态或重新准备。
   另做一次准备期间回桌面再返回，观察是否可继续或可恢复重试。

**记录：** 取消是否实际命中、重试/重新准备结果、耗时、前后台结果、异常退出次数。
100% 下载不等于检查完成；ready 不代表已渲染页面、保存阅读位置或阅读统计。

## 8. 可选大样本：建议本轮完成（AC7/AC10）

用户可跳过，但跳过则近上限真机项仍为 `unverified`，不能据此关闭 AC10。
由协调者在已配置 Dart 依赖的项目根生成文件；以下只写忽略目录，工具本身不修改：

```powershell
New-Item -ItemType Directory -Force local-evidence/s3 | Out-Null
@'
import '../../tool/reader/publication_memory_fixture.dart';
void main() => writePublicationMemoryFixture('local-evidence/s3/synthetic-near-limit.epub');
'@ | Set-Content -Encoding utf8 local-evidence/s3/generate_fixture.dart
dart run local-evidence/s3/generate_fixture.dart
(Get-Item local-evidence/s3/synthetic-near-limit.epub).Length
```

该函数生成约 200 MiB 的 stored ZIP（200 个各 1 MiB 的合成图片条目），接近
256 MiB 文件上限但非极限值；图片为小 PNG 加填充，仅用于准备/资源实验。
直接运行 `publication_memory_probe.dart` 会自动删除临时样本，不能用来保留上传文件。

1. **用户自行**在自己的 lan-reader 网页上传该 EPUB 到 NAS；这是用户对书库的操作，
   不是 Shiori 的上传能力，也不授权代理写 NAS 或修改参考 checkout。
2. 在 Shiori 刷新，选合成书，按第 7 节取消后重试，等到 ready。准备期间观察界面响应，
   记完成时间、是否退回桌面、是否出现启动画面或状态丢失；完成后再开普通书确认可用。

**预期 / 记录：** 完成准备，未观察到内存终止；记录实际字节数、尝试/成功/取消/退出数。
若异常退出，保留时间及可取得的系统分析/Jetsam 记录，原因待查；无峰值测量则写“未测”，
不能填 0。此项不证明图片解码、排版、全流程 RSS 上限或 S4 阅读性能。

## 9. 无效候选服务器与返回（AC1/AC2/AC3）

1. 在服务器 A 正常时进入“更换服务器”，输入 `https://candidate.invalid` 点“连接”。
   失败后应有可恢复说明，原服务器 A 仍为当前连接；返回书库能继续浏览 A。
2. 再尝试候选地址，在验证中点“取消”（来不及时记未覆盖），返回 A 并刷新；
   旧请求结束后不应覆盖当前界面。重新进入连接页，应仍显示 A。
3. 若用户已有第二个可用部署 B，可另测 A → B → A，并在准备期间切换，
   检查列表、封面、ready 不串库；没有 B 就把跨有效服务器项记 `unverified`。

**记录：** 候选失败/取消、A 保留和延迟回调观察结果。无效 B 不算完整 A → B → A
竞态证明；401/403、TLS、登录代理等未实际出现的错误分类也不标为真机通过。

## 10. 重启与第二个产品包覆盖更新（AC1/AC6/AC8/AC10）

1. 在线状态下从多任务界面划掉 Shiori，再从桌面启动。应恢复服务器 A 并加载书库，
   无需重新填地址；再准备普通书。记录恢复、准备、旧导出是否正常。
2. 协调者对已审核 ref **新建一次 `mode=app` dispatch**，可使用同一提交，
   取得更高 run number/build number；不要只 Re-run 原 run（不会增加 run number）。
   若需推新提交，先取得该次具体 push 授权。
3. 重复第 2–3 节核对与签名，用同证书/描述文件、同 bundle ID 覆盖安装，
   不卸载。核对新 build number > 旧值；产品无版本展示入口时保留签名工具的版本截图。
4. 启动应仍恢复 A、显示原书库；再打开/准备普通书，检查旧 Documents 导出未变。
   缓存可被系统清理，允许重新下载；ready 文案不要求跨进程原样保存。

**记录：** 两个 build ID/number、签名身份一致性、无需重设、书库/准备/导出结果。
这验证实际持久化行为；产品内没有 SQLite 六步自检或原始状态导出入口，
不据此宣称完整迁移、future-schema 拒绝、故障注入或缓存预算已在设备重测。

## 11. 收集并回传结果

1. 截图/录屏留在手机，笔记用代号和步骤号。经“文件”保存/分享笔记与已有导出到电脑，
   将照片中的截图另行传回，统一存入 `local-evidence/s3/<SESSION>/`；
   例如 `04-denied.png`、`07-ready.png`、`notes.txt`。
2. 已有 Shiori 导出可从“文件 → 我的 iPhone → Shiori”分享；有 USB 时也可用
   Apple Devices 的“文件 → Shiori”保存。产品不会自动产生 S1 probe 的 JSON，
   Application Support 数据库也不会出现在“文件”中；不要找不到就重装。
3. 核对电脑文件非空、可打开，笔记对应正确 build。私密原件保持忽略，
   对外只发脱敏表、build/run、成功/失败数及异常说明；截图须先遮住地址、书名、作者、
   证书身份和系统个人信息。若需协调者分析原件，告知其本地相对路径即可。
